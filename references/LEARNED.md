# 经验沉淀（每次解决卡点后必须往这里写）

> **这个文件是「卡点学习模式」的落地处。**
> 按 SKILL.md 的纪律 2：同一环节连续失败 2 次、或重试 3 次无进展，
> 就要请用户手动操作一遍并把过程回传，然后把学到的东西写进这里。
>
> 只改代码不写这里 = 下次还会踩同一个坑。

## 记录格式

```
## YYYY-MM-DD · 环节名 · 一句话现象

- **现象**：用户/脚本看到了什么
- **根因**：为什么会这样（不要只写"改了选择器"，要写为什么原来的不对）
- **解法**：具体改了什么（文件 + 关键代码/配置）
- **验证**：怎么确认真的解决了
- **来源**：自己debug / 用户手动操作后回传
```

## 2026-09-17 · 番茄签署 · 签完后签署页会「跳走」，「签署成功」四个字随之消失 → 脚本永远等不到

- **现象**：用户 19:33 说「已发布了」，而脚本 19:36 还在打印
  「· 等待你完成签署…（剩余约 24 分钟，浏览器保持打开）」，会一直空等到 30 分钟超时。
- **根因**（**用户口述 + 后台核对双重确认**）：
  **签署成功后，电子签页会自己跳走（回到登录页 / 首页），「签署成功」那段文案随之消失。**
  而原策略是「每轮扫所有标签页正文，找 `SIGN_DONE_KEYWORDS`」——
  等你签完，那四个字已经不在页面上了，**这个判据天然会错过正确时机**。
  ⚠️ 更早一次（2026-09-12）能检测成功，是因为当时签署页**没跳走**；
  这次跳走了就失效 —— 说明这个判据**不可靠，不能当唯一依据**。
- **解法**（`fanqie_upload.py` `step3_sign_contract` 的等待循环）新增两个判据：
  - **B. 签署页「全都消失了」**：`sign_seen_once=True` 且当前 `sign_pages(ctx)` 为空
    → 判定签完（用户证实的跳走行为）。
  - **C. 签署页变成登录页**：曾见过签署页，现在正文出现
    「重新登录 / 请登录 / 手机号登录 / 扫码登录」→ 同样判定签完。
  保留原判据 A（正文关键词）作为兜底。三者任一命中即 `mark_published()`。
- **验证**：后台核对 4/4 在列表里、状态「审核中」（=发布成功），
  创建时间 `2026-09-17 19:28`，ID 见 `out/batch3-20260917.progress.md`。
- **教训**：**「成功状态会自己消失」的流程，不能只靠轮询页面文字判成功。**
  要额外用「状态载体消失/迁移」这类**负向信号**（页没了、跳走了）来判定。
- **来源**：★ **用户主动告知**（「平台跳出签署完成后它会自动关闭窗口并显示重新登陆页面，
  其实已经发布完成了」）

## 2026-09-17 · 全仓库 · 脚本用「脚本所在目录」当工作目录，用户在别处跑就全线找不到文件

- **现象**：`fanqie_upload.py` 报
  `[WinError 3] 系统找不到指定的路径。:
   '...\skills\music-workflow\scripts\library\踏月寻你-01\audio.mp3'`，
  且歌名被记成 `踏月寻你-01`（而非 meta 里的 `踏月寻你`）。
- **根因**：`fanqie_upload.py` 写死
  `ROOT = Path(__file__).resolve().parent`（注释还写着「脚本所在目录 = 工作目录」），
  于是 `LIB_ROOT / PUBLISHED_FILE / SMS_FILE / LOG_PATH` **全部指向 skill 内部**。
  用户在 `--workdir` 目录跑时：① 找不到文件；
  ② `meta.json` 读不到 → `load_song()` 退回目录名当歌名 → 上传成「踏月寻你-01」。
  （`miaoxiang.py` 早就支持 `--workdir`，只有番茄端漏了，属**一致性缺口**。）
- **解法**：`fanqie_upload.py`
  - 拆出 `SCRIPT_DIR`（只用于 import 兄弟模块）；
  - `ROOT = MW_WORKDIR 环境变量 > 当前目录(有 tasks.csv) > 脚本目录`；
  - 新增 `--workdir` 参数，在 `main()` 里**重新计算**
    `ROOT/LIB_ROOT/PUBLISHED_FILE/SMS_FILE/LOG_PATH` 五个全局；
  - `_sys.path.insert()` 改用 `SCRIPT_DIR`（模块在脚本目录，不在数据目录）。
  - 同类问题也修了 `verify_published.py` 的 `workdir()`（加当前目录自愈规则）。
- **验证**：`load_song()` 对 4 个目录全部 `文件齐=True`，歌名正确取到
  `踏月寻你` / `踏月寻你（动听版）`；上传日志显示歌名正确。
- **教训**：**「脚本目录 == 数据目录」这个假设一旦被 `--workdir` 打破，
  所有模块级 DATA 常量都会静默指错。** 新增数据类路径时先问「它跟工作目录走吗」。
- **来源**：自己 debug（用户 19:14 让我重试，发现路径报错）

## 2026-09-17 · 后台核对 · `verify_published.py` 把 `-02` 的 ID 显示成 `-01` 的（自证工具本身出错）

- **现象**：核对输出里 `踏月寻你-01` 和 `踏月寻你-02` **打印同一个 ID**，
  但后台列表明明有两条不同记录（`踏月寻你` / `踏月寻你（动听版）`）。
  → 若没发现，就会把「核对通过」建立在错误的对照上（纪律 3 的工具自身不可信）。
- **根因**：两层叠加
  1. `workdir()` 在没设 `MW_WORKDIR` 时静默退回 skill 目录 → 那里没有 `library/`
     → `folder_display_title()` 取不到 `meta.json` → 退回**目录名** `踏月寻你-02`；
  2. 退回的短名 `踏月寻你-02` 与后台的 `踏月寻你` 互相包含（`r.name in t` 命中）
     → 双双匹配到同一行。
- **解法**：
  - `workdir()` 增加「当前目录有 `tasks.csv` 或有 `library/` 即视为工作目录」；
  - `folder_display_title()` 兜底路径**也剥掉结尾 `-01`/`-02`**，
    保证最差情况下也退回干净歌名。
  - 保留「精确优先、其次取最长名」的匹配顺序（防短名吃长名）。
- **验证**：重跑后 4 个目标各拿到**互不相同**的 ID：
  `...844555838` / `...848733758` / `...852944446` / `...852928062`。
- **来源**：自己 debug（核对输出自相矛盾引起怀疑）

## 2026-09-17 · 妙响下载 · 「兜底顶包」把 A 歌的音频静默存成了 B 歌（3 份文件 MD5 完全相同）

- **现象**：批 3 跑完，`library/踏月寻你-01/audio.mp3`、`library/同路一程又一程-01/audio.mp3`
  以及备份里的原件，**三份 MD5 全等于 `27efa0b8…`**；下载日志里文件名还叫
  `同路一程又一程.mp3`（当时正在下的是《踏月寻你》）。**没有任何报错。**
- **根因**：`download_exported()` 里有一段「兜底」：
  ```python
  if card is None:
      cand = cards.first      # ← 抓第一张「编辑器导出」卡
  ```
  平台「并轨导出」要几分钟才产出新卡，而 `filter(has_text=title)` 是**当场查**，
  查不到就直接抓了**上一轮遗留**的导出卡。于是下载到的永远是同一个人（最早那张），
  但被按当前歌名入库 → **张冠李戴且静默**。
  这比崩溃危险：崩溃会停，静默错误会一路带到发布环节。
- **解法**：
  1. **删掉兜底顶包**。改成三段式：按名精确匹配 → 轮询等「不在 `before_exported` 里的新导出卡」
     （上限 6 分钟）→ 等不到就**抛错**。新增 `before_exported` 参数，调用前先快照已有导出卡。
  2. **加 MD5 防重护栏**（`save_song()`）：本批内 + 跨 `library/` 目录双向比对，
     撞了就**拒收**并打「疑似下载张冠李戴」。这是最后一道网 —— 就算定位逻辑再错，
     也不会把同一音频存成两首。
  3. CLI 加 `--card "卡片签名=歌名"`，显式指定映射，替代「最新 N 张」的猜测。
- **验证**：重下后 4 个文件 MD5 两两不同
  （`27efa0b8` / `6c410586` / `5c5b00bb` / `c5d375cf`），
  且文件大小与卡片时长对得上（6.17MB↔03:22、5.56MB↔03:02、4.8MB↔02:37、4.9MB↔02:41）。
- **教训**：**「找不到就退而求其次」在数据写入路径上是反模式。**
  宁可报错让人来看，也不要猜一个填上 —— 猜错了没人知道，等发现时已经发出去了。
- **来源**：用户反馈「第二版导出超时了，你再试一次」→ 复核文件发现 MD5 相同

## 2026-09-17 · 妙响取卡 · 骨架卡（innerText=''）被当成新卡 → 「找不到卡片：」冒号后为空

- **现象**：日志 `✗ 第 1 版失败：RuntimeError: 找不到卡片：` —— **冒号后面什么都没有**。
  卡片数量检查却过了（`这一轮新出 2 张`）。
- **根因**：`CARDS_JS` 只做 `querySelectorAll('[class*="generatedSongListItem"]')`，
  把**还在渲染的骨架卡**也吐出来，其 `innerText` 是空串。
  于是「够数了」但 `sig=''`；`locate_card_index` 里 `key` 为空 → `return -1` → 报错。
- **解法**：新增 `CARDS_JS_STRICT` + `_cards_strict()`：
  只要「签名非空 **且** 含 `mm:ss` 或 `YYYY-MM-DD`」的真卡（骨架卡两者都没有）。
  `wait_new_cards` 与 `do_gen` 的 `before` 快照**统一走 strict**，避免口径不一致。
  `locate_card_index` 也改成三层降级（前缀精确 → 歌名包含 → 可读报错）。
- **验证**：批 3 复发时 2/2 卡正常定位并按名匹配到导出卡。
- **⚠️ 坑中坑**：真卡的 `innerText` **本身已含**「编辑器导出」四字，
  所以 strict 版**不要**再补这个后缀，否则变成「…编辑器导出…编辑器导出」，前缀匹配反而断。
- **来源**：自己 debug（批 3 第一轮日志）

## 2026-09-17 · 妙响版本号 · `version_index` 用 enumerate 序号，某版失败时错位

- **现象**：`library/踏月寻你-01/meta.json` 里出现
  `"title": "踏月寻你（动听版）"` 与 `"version_index": 0` **自相矛盾**。

- **来源**：自己 debug（入库结果复核）

- **现象**：自动跑完，脚本在 19:04:27 点「跳转授权」→ 19:04:30 新开电子签标签 →

  ✓ 好日子咱一起走          [审核中] ID 7684602153356250136  创建 2026-09-12 19:01
  ✓ 好日子咱一起走（动听版）    [审核中] ID 7684602153360444440  创建 2026-09-12 19:01

## 2026-09-12 · 番茄上传 · 判断「签署页开没开」不能用正文文字，要用 URL；否则会重复开签署页

- **现象**：用户反馈（原话）：「**跳转成功就可以了，不需要重复跳新开多个页面，
  只需要打开一个签署页面就可以了。**」——实际多开了一个签署页。
- **根因**：两层叠加 ——
  1. `click_jump_authorize` 判「到没到电子签页」看的是**正文里的特征词**
     （`电子牵/letsign/选择签章/意愿认证/文件签署`），但 `contract.feishu.cn/h5/sign/signLink`
     这种 h5 页**正文里根本没有这些词**（慢加载 + 文案不同）→ 永远判成「还没到」；
  2. `step3_sign_contract` 里有个兜底逻辑：`if not esign_seen:` 就每 30 秒补点一次
     「跳转授权」。由于条件①永远为真，**它每 30 秒就点一次** → 多开一堆签署页。
     日志实证：19:05:00 `· 番茄页仍有「跳转授权」，已替你补点一次`。
- **解法**（`scripts/fanqie_upload.py`）：
  - 新增 `SIGN_URL_MARKS` / `is_sign_page()` / `sign_pages(ctx)` —— **一律用 URL 判断**
    签署页是否已打开（`contract.feishu.cn`、`letsign.com`、`sign/signLink`、`esign`、`/sign`）；
  - `click_jump_authorize`：点完「跳转授权」后**先等最多 20 秒**看页面开没开，
    开出来就立刻 `return`；只有**确认没开出来**才允许再点，`MAX_CLICKS` 从 4 降到 **2**；
  - `step3_sign_contract`：兜底补点改为 `MAX_NUDGES = 1`（全程最多 1 次），
    且**只要已有签署页就绝不补点**；
  - 新增 `dedupe_sign_tabs(ctx)` —— 万一真多开了，**自动关掉多余的，只留第一个**。
- **验证**：编译通过；`is_sign_page` 对本次真实 URL
  `https://contract.feishu.cn/h5/sign/signLink?url=https://s.letsign.com/MNjMedLjJqQ/` 判定为 True。
- **来源**：用户反馈

## 2026-09-12 · 全仓库 · 「清理残留浏览器」按进程名一刀切，误杀用户自己的 Chrome

- **现象**：用户发现**自己正在用的 Chrome 被脚本杀掉了**。用户原话指出这是危险操作并要求修掉。
- **根因**：`browser_utils.kill_browsers()` 的实现是
  `for name in PROCESS_NAMES: taskkill /f /im <name>`，而
  `PROCESS_NAMES = ["chrome","chrome.exe","chromium",...,"msedge.exe",...]`。
  Playwright 拉起的浏览器**进程名也叫 chrome.exe**（它是 Chromium 内核），
  所以「按名字杀」等于「把用户所有 Chrome 一起杀」。
  同一个危险写法还散落在 `login_check.py` / `inspect_buttons.py` /
  `probe_generate.py` / `probe_popup.py` 四处兜底分支里。

## 2026-09-01 · MiniMax 生成 · 数量还是出两首（第一版修复没真修好）

- **现象**：上一版（08-30）改了 `quantity_per_round=1` 还新增了 `set_generate_quantity()`，

     `btns[0]` 变成「参考音乐上传」按钮——点减号根本不作用于数量。

  1. **定位**：找页面上的「纯数字 span」，它的**父容器恰好有 2 个按钮**的就是 stepper
     （第一个按钮=减、最后一个=加）。这样不会误命中大容器。
  2. **改值**：点减/加按钮一步步走到 `want`；点击用**原生 `el.click()`** 触发 React 合成事件，
     绕过 Playwright 的可点击性/遮罩检查（这类 Tailwind 自定义按钮常被误判为点不到）。
  3. `quantity_per_round` 默认 1 保留；`selectors.quantity` 的 input/minus/plus 仅作兜底（antd 等其它形态）。
- **验证（真页面，最有说服力）**：`verify_qty.py` 打开真实页面，
  读取修改前后值 —— 2→1、1→3、3→1 全部生效，函数返回 True。

  专门复现"误命中大容器"）跑 4 项全过。
- **来源**：用户实测反馈「还是出两首」

> **教训（叠加 08-30）**：① 修"页面操作类"bug **不要猜 DOM 结构**——先用 `diag_qty.py` 抓真实 DOM 再写选择器；

- **根因**：`generate.py` 把浏览器视口**硬编码**成 `viewport={"width": 1440, "height": 900}`。
  在屏幕小于 1440×900 的设备上（实测 1280×720），页面按 1440 宽渲染，比屏幕还大，
  横向溢出 + 底部按钮落在视口外。`fanqie_upload.py` 虽然 `--start-maximized`，
  但没设 `viewport=None`，Playwright 默认视口 1280×720 照样覆盖窗口尺寸，页面不跟随窗口。
- **解法**：
  1. `browser_utils.py` 新增 `window_args(headless)` / `viewport_for(headless)`：
     有头模式 `--start-maximized` + `viewport=None`（页面跟随窗口自适应），
     headless 模式才给固定视口兜底。
  2. `generate.py`、`fanqie_upload.py` 全部改用它，删掉手写视口。
  3. 点击/填写前 `scroll_into_view_if_needed()`（长页面底部按钮先滚到可见）。
- **验证**：真起有头 chromium 实测，页面视口 = 屏幕可用尺寸（1280×720 = 1280×720）。
- **来源**：用户反馈（换设备后用） + 自己实测

> **教训**：**不要硬编码浏览器视口。** 固定 1440×900 只对作者自己的屏幕成立，
> 换台设备就溢出。正确姿势是"有头 = 最大化 + 跟随窗口，headless = 才给固定值"，
> 参数封装成公共函数让所有脚本共用（不然各写各的又会有漏网的）。
> 这台设备实测就是 1280×720 —— 固定 1440 的视口比屏幕还宽，必然溢出。

## 2026-08-30 · MiniMax 生成 · 守卫认不出弹窗容器（靠猜 class 名字的必然结局）

- **现象**：MiniMax 登录后弹活动公告（要手动点 ❌），守卫关不掉，生成流程卡死。
- **根因**：为了安全，关闭按钮的查找范围被限定在**已知弹窗容器白名单**里。
  但 MiniMax 的容器是 `<section class="responsive-modal z-[1050]">`，**不在名单里**，
  守卫连找都没往里找。用 `[class*='-close']` 也没用：❌ 的 class 是 `icon-btn`，不带 close。
- **解法**（三层，全部建立在"作用域"上，不是扫描整个页面）：
  1. **遮挡浮层作用域**（`use_overlay_scope`，默认开）：凡是
     `fixed/absolute + z-index≥100 + 覆盖≥40% 屏幕` 的元素，一律也算作用域。
     ★ **靠"它挡住了屏幕"这个行为识别，跟它叫什么名字无关** —— 这是根本性修复。
  2. **角落兜底**：× 连 close 类名都没有时，按「在对话框右上角 + 尺寸≤64px +
     内容是 ❌/×/✕」来认。
  3. 用户把实测到的容器选择器加进 `extra_popup_roots`（双保险）。
- **验证**：`test_popup_guard.py` 新增测试 12/13/14/15，覆盖
  「容器非标准」「❌ 无 close 类名」「MiniMax 真实结构（icon-btn）」
  「MiniMax 真实结构（aria-label='close'）」。30/30 通过。
- **来源**：用户反馈 + 用户补充真实容器选择器 + 自己写测试复现

> **教训（两个）**：
>
> 1. **靠名字识别不可靠，要靠行为。** 猜 class 名字（白名单）永远有漏网的，
>    因为网站可以起任何名字。而"它挡住了屏幕"是**行为层面**的判据，与命名无关。
>    安全与能力不是二选一 —— 把作用域限定到"确实构成遮挡的元素"，既安全又通用。
>
> 2. **角落兜底要按"对话框面板"的右上角算，不能按"整屏遮罩"的右上角算。**
>    这个 bug 我差点漏掉：对话框居中时（460px 宽 / 1440px 视口），它的右上角跟
>    遮罩的右上角差了近 500px，按遮罩算会**全部漏判**。
>    写完先跑测试才发现 —— 又是一次"不写真机测试根本发现不了"。

## 2026-08-30 · 全环节 · 打开页面后弹窗挡路，自动化卡住不动

- **现象**：打开 MiniMax 音乐创作页后有时弹出浮层，脚本不关掉就执行不了下一步，
  表现为「点了生成没反应」「填表填到一半卡住」。
- **根因**：两个层面都没处理。
  1. 脚本里全是裸 `page.goto()` 和裸 `click()`，**没有任何弹窗处理逻辑**
     （`grep dialog` 在两个脚本里都是 0 处命中）。
  2. 更隐蔽的是：最麻烦的浮层是「整屏半透明遮罩 + 没有关闭按钮」，
     它会把**关闭按钮自己也挡住**。所以哪怕写了"点 × 关闭"也照样点不动——
     Playwright 报 `intercepts pointer events` 然后超时。
- **解法**：新建 `scripts/popup_guard.py`（同步版给 generate.py，异步版给 fanqie_upload.py），
  按「点 × → 点文字按钮 → 按 Esc → **铲掉纯遮罩再回到第一步重来**」的顺序循环处理。
  判断"纯遮罩"的依据是内部**没有任何可交互元素**，真正的对话框因此被跳过、不会误删。
  集成点：`guard_context()` 挂原生弹窗处理器、`goto_with_guard()` 替换所有裸 goto、
  `try_click(..., cfg=cfg)` 点不动时自动清弹窗再重试一轮。
- **验证**：新增 `scripts/test_popup_guard.py`，真起 chromium 构造三种弹窗实测，**14/14 通过**。
- **来源**：用户测试反馈 + 自己 debug（先写测试跑出失败，才暴露出下面的两个实现 bug）

> **自己写的代码被自己的测试抓出两个 bug**（值得记下来）：
> 1. **顺序错了**——把"铲遮罩"当最后兜底，结果第一轮点 × 就被遮罩挡住，后面全废。
>    必须把铲遮罩纳入**每一轮**的升级链条。
> 2. **循环提前 `break`**——第 0 轮没命中就退出，根本走不到铲遮罩那一步。
>    正确做法是"一整轮下来什么都做不了"才 break。
>
> 这两个 bug 单看代码都很合理，**不写真机测试根本发现不了**。

> **顺带纠正一个想当然的说法**：我一开始在文档里写"原生 alert 不处理会让页面一直挂起"。
> 用对照实验验证后发现是错的——**Playwright 在没有 dialog 监听器时会自动关闭原生弹窗**，
> 通常不会卡住。真正危险的是 DOM 浮层。挂处理器的实际价值是：能看到弹窗说了什么
> （如"额度用尽"）、`beforeunload` 不会被自动关闭、以及排掉"别处注册了监听器却没处理"的雷。
> **没有验证过的断言不要写进文档。**

> 源目录永远缺不了文件，这类 bug 在那里根本露不出来。

## 2026-08-30 · 番茄上传 · 弹窗守卫把用户已填的歌手名等四个标签全删了（最严重的一次）

- **现象**：上传多首歌时，从第 2 首开始，第 1 首卡片里已填好的
  「歌手名 / 词作者 / 曲作者 / 制作人」四个标签**全部被清空**。
- **根因**：为了让自动化不被弹窗卡住，我写了 `popup_guard.py` 自动关弹窗，
  实现方式是**在整个页面扫 class 里带 close 的图标**（`[class*='-close']`、
  `[class*='close-icon']`、`[aria-label='关闭']` 等 32 种）然后逐个点掉。
  但这四个字段是**标签式输入框**，每个已填好的标签旁边都有一个删除用的 ×
  （形如 `.tag-close-icon`）—— 它跟"关闭弹窗"的 × 长得一模一样。
  上传第 2 首歌时，页面上还留着第 1 首填好的四个标签，于是一次性全被点掉。
- **解法**（改的是设计，不是改选择器）：
  1. **关闭按钮只在「可识别的弹窗容器」里找**（`popup_roots` 白名单：
     `.ant-modal-root` / `.arco-modal-wrapper` / `[role='dialog']` / `[aria-modal='true']` 等 19 种），
     **绝不扫描整个页面**（`scan_whole_page` 默认 `false`）。
  2. `dangerous_selectors` 黑名单兜底：`.ant-tag-close-icon`、
     `.ant-select-selection-item-remove`、`[class*='clear-icon']` 等，命中即跳过。
  3. 文字拦截：含「删除 / 移除 / 清空 / 注销 / 解绑 / 放弃 / 终止」的按钮**一律不点**。
- **验证**：`test_popup_guard.py` 新增测试 6（已填标签一个不能少，同时真弹窗照关）、
  测试 10（"确认删除"弹窗宁可不管也不能点）。21/21 通过。
- **来源**：用户实测反馈 + 自己写测试复现（先写测试证明 4 个标签确实被删，再动手改）

> **教训（这条最该记住）**：**语义相反的两个控件可以有完全一样的外观和 class。**
> 「关掉弹窗」的 × 和「删掉这条内容」的 × 长得一模一样，靠猜 class 名字区分必然出事。
> 正确做法是**用"它在哪儿"来判断**（是否在弹窗容器内），而不是"它长什么样"。
>
> 更一般地说：**自动化去点页面上的东西之前，必须能回答"点了会发生什么"。**
> 答不上来就不要点 —— 宁可流程卡住让人来处理，也不能静默删掉用户的数据。
> 卡住是可见的、可恢复的；数据被静默清空则可能根本没人发现。

## 2026-08-30 · 番茄上传 · 弹窗要点「确认」而不是删掉遮罩（用户明确指出）

- **现象**：我原先用"删掉挡路的整屏遮罩"作为兜底手段，保证点击能进行下去。
- **用户反馈**：「弹窗信息你只要点确认就好了，它会自动关闭，不用总是删掉，
  这样会误删一些重要的弹窗信息，影响后面执行」。
- **根因**：删遮罩是**绕过页面自身逻辑**的粗暴做法 —— 直接把 DOM 移除，页面却以为
  弹窗还开着，内部状态不一致；更要命的是会连带干掉那些**需要人看一眼**的重要弹窗
  （额度提醒、验证提示、授权确认），后面的步骤反而因此出错。
- **解法**：策略改成"先礼后兵"——
  ① × 关闭按钮 → ② 弹窗底部主按钮（番茄裁剪弹窗就是这种，文案可能是"确定/保存/完成"）
  → ③ 确认类文字按钮 → ④ 关闭类文字按钮 → ⑤ Esc → ⑥ 删遮罩（**默认关闭**）。
  点确认走的是页面自己的关闭流程，弹窗会自己关掉，页面状态也保持一致。
- **验证**：测试 7（"我知道了"必须压过"以后再说"）、测试 8（遮罩默认保留，
  显式 `force_mask=True` 才删）、测试 9（Arco footer 主按钮能认出来）。
- **来源**：用户反馈

> **教训**：**优先走页面自己的正常路径，不要绕过它。**
> 点"确认"是页面设计好的关闭方式，删 DOM 是硬来。能用正常路径就别用 hack。
> 这也解释了上一版的删遮罩为什么错：它解决了"点不动"这个表象，
> 代价是破坏页面状态 —— 典型的"治标，且带来新问题"。

## 2026-08-30 · 歌名含逗号 · safe_name 会把全角标点转成半角（验证中发现的隐患）

- **现象**：歌名《晚风，寄的信》经 `generate.py` 的 `safe_name()` 处理后，
  文件夹名变成 `晚风,寄的信`——中文全角逗号「，」被转成了英文半角逗号「,」。
- **根因**：`safe_name()` 里用了 `unicodedata.normalize("NFKC", name)`。
  NFKC 归一化会把全角标点统一转成半角，而**英文逗号不在非法字符过滤列表里**
  （列表只过滤 `\/:*?"<>|`），于是半角逗号被保留下来。
- **为什么危险**：`fanqie_upload.py` 的 `--mark-published` 和 `--songs`
  都是**用英文逗号分隔**参数的。一旦歌名含半角逗号，
  `--mark-published 晚风,寄的信` 会被拆成「晚风」和「寄的信」两个名字，
  防重复记录会静默失效（不报错，但记为错误的名字，下次照样重复发）。
  同理，上传到番茄平台的歌名会显示成半角逗号，中文排版下很难看。
- **根本修复（已完成）**：`safe_name()` 里加一行 `name.replace(",", "，")`，
  归一化后把半角逗号换回全角——既保住中文排版，又不会被参数分隔符误伤。
- **用法提醒**：尽管如此，歌名仍建议尽量简洁、少用标点。
- **验证**：改用无逗号歌名后，`safe_name()` 输出与原歌名一致，`--mark-published` 解析正常。
- **来源**：自己 debug（本次「发布前再验证一遍」时扫描出来的）
- **教训**：**NFKC 归一化 + 逗号分隔参数 = 静默失效的定时炸弹**。
  凡是"用户输入会变成文件名、又会被塞进逗号分隔列表"的地方都要查一遍。

> ⚠️ **写文档时的注意事项**（2026-08-30 公开前扫描发现）：
> 本文件在记录这个坑时，曾直接用**真实作品名**当例子，
> 结果把使用者的实际作品信息带进了公开仓库（写这条教训时又差点犯同样的错）。
> **规则：文档、模板、注释里举例一律用虚构歌名**（如《晚风，寄的信》），
> 绝不出现任何真实发布过的作品名。每次公开前按同样方式扫一遍。

> 顺带：这次是用户要求「上传前再验证一遍 skill 是否可靠」才发现的。
> **没跑过的路径就是没验证过的路径**——之前的歌名恰好都没逗号，所以从没暴露。

## 2026-09-01 · 番茄第三步 · 合同签署按钮被遮挡点不到（a3cc6d6 没覆盖到）

## 2026-09-01 · 数量控件改了"别的数字" · set_generate_quantity 静默误命中（第三版修复）

- **现象**：用户截图铁证——页面「数量：2 +」**仍然是 2**，
  但脚本日志写 `✓ 生成数量已设为 1（原 2）`。结果每首歌词点一次生成出 **2 个版本**
  （《陪你慢慢变老》×2、《母亲的缝纫机》×2），用户明确要求"一首词出一首"。
- **根因（比前两版更深）**：
  `set_generate_quantity()` 的 JS_FIND 用「纯数字 span + 父容器恰好 2 个按钮」定位 stepper。
  但页面上**不只有一个满足此条件的数字 span**——可能还有其他控件（标签数字、计数器等）
  也恰好是"数字 span + 父容器有 2 按钮"。脚本**命中了错误的那个**，点了它的减号，
  读回值确实从 2 变成 1（因为改的就是那个错误控件的值），于是报"已设为 1"——
  **真正的数量控件纹丝未动**。
  这是"看起来成功了"的**最阴险形态**：不是报错、不是超时，而是**静默改错了对象还报成功**。
- **正确解法（锚定「数量」标签）**：
  JS_FIND 必须先找含 **「数量」** 文字的标签元素（兼容 `数量：` / `数量:` / `数量`），
  再从这个标签的父/兄弟容器里定位数字 span + 减/加按钮。
  这样即使页面上有其他"数字+2按钮"的控件也不会被误命中——
  因为只有**紧挨着「数量」标签的那个**才是真正的 stepper。
  兜底保留旧逻辑（页面改掉标签文字时降级）。
- **附带修：生成按钮文案又变了**
  按钮探测显示按钮文本现在是 `600\n创作`（额度+换行+"创作"），

## 2026-09-20 · 存储 · 「歌曲能不能放 D 盘」——曲库散落 8 处，300 MB 全在系统盘

- **现象**：用户提「批量下载比较占用 C 盘，能放 D 盘吗」。
- **实测（别猜，先量）**：
  - 曲库不是「一个」，是**散在 8 个目录**里，共 **45 首 / 299.1 MB**，全在 C 盘 ——
    因为工作目录跟着**会话日期**走（`WorkBuddy/<日期>/...`），每开一批新会话就多一个曲库。
  - 登录态另外占 **602 MB**（`%LOCALAPPDATA%/music-workflow/profiles/`：
    douyin 402 + profile 95 + profile_fanqie 105）。
- **代码里两个真问题**：
  1. **下载中转写死系统盘**：`miaoxiang.py` 里 `tempfile.mkdtemp()` 用的是系统 TEMP
     （`%LOCALAPPDATA%/Temp`），而且 `save_song()` 是 **copyfile 不是 move**，
     临时文件根本不回收。→ 即使曲库在 D 盘，下载过程仍会占 C 盘。
     （实测 TEMP 里没攒下残留 —— Windows 会清，但**峰值占用是真的**。）
  2. **三个脚本的工作目录解析口径不一致**：`miaoxiang.py` 认 `--workdir` → cwd → 脚本目录；
     `fanqie_upload.py` 认 `MW_WORKDIR` → cwd → 脚本目录；`verify_published.py` 还多一层 config。
     → 一旦「把曲库挪到别的盘」这个新概念进来，三处必然各走各的。
- **解法**：
  - `paths.py` 新增设置文件（`%LOCALAPPDATA%/music-workflow/settings.json`）承载
    `workdir` + `temp_dir`，并新增 `default_workdir()` / `work_temp_dir()`；
  - `miaoxiang.py` 加 `--set-workdir`（一条命令设定，起浏览器之前就 return）；
  - **设置文件的优先级故意高于「当前目录」** —— 用户设完「都放 D 盘」后，
    在哪儿敲命令都该落 D 盘；
  - 下载中转改为 `<workdir>/.tmp/`（`tempfile.mkdtemp(dir=...)`），新增模块级
    `_ACTIVE_WORKDIR` 在 `resolve_workdir()` 里设一次，保证「中转跟曲库同一块盘」；
  - `fanqie_upload.py` / `verify_published.py` 的解析链同步插入 `default_workdir()`。
- **新增 `migrate_library.py`**（只复制、校验、不删除；`--purge` 才删）：
  - **主力曲库 → `<目标>/library/`，历史目录 → `<目标>/_archive/<来源>/`，绝不合并。**
  - **为什么不合并（关键判断）**：`music-factory` 那 18 首**没有 `published.json`**，
    但那是「当时还没有这个机制」，不等于「没发布过」。合并进主力曲库 →
    上传脚本认为都没发过 → **重复投稿**。`_archive/` 不在曲库扫描路径上，
    脚本看不见，所以安全。
  - 校验方式：文件数 + 总字节数 + **音频逐首 MD5**，任一不一致就 fail 并拒绝 `--purge`。
- **踩到的实现坑**：`--set-workdir` 会**预先建好空的 `library/`**，而 `copy_verify()` 原本
  「目标存在就改名加 `__dup2`」→ 会把主力曲库搬成 `library__dup2`。改为
  「存在**且非空**才改名」，`shutil.copytree(..., dirs_exist_ok=True)` 复用空目录。
  另外 `copy_verify()` 只返回 `(ok, msg)`，但 dst 可能被改名，**报告里必须写真路径**
  → 改成三返回值。
- **验证**：45 首全部 MD5 校验通过；D 盘 `library/` 16 首（含已发布的 4 首）+
  `_archive/` 7 个目录 29 首；`default_workdir()` / `work_temp_dir()` 与三个脚本的
  解析结果全部指向同一目标盘。
- **来源**：用户提问「你这些下载的歌曲信息能放到 D 盘吗，因为批量下载比较占用 C 盘内容」

> **教训**：
> ① **用户问「能不能放 X 盘」时，先量再答**。别假设「曲库就一个」——
>   实测是 8 个散落目录。先跑一遍清点，才知道该搬什么、有没有重复投稿风险。
> ② **「换个存储位置」这种需求，真正的成本在「让所有脚本口径一致」**，
>   不在复制文件本身。三个脚本三套解析逻辑，加一个新概念就会分裂 ——
>   所以本次把解析入口统一收进 `paths.py`。
> ③ **数据搬迁的铁律：只复制、逐项校验、原件等用户确认再删**。
>   并且**归档与主力必须分开**，因为「看不见 = 不会误操作」比「加个判断」可靠得多。

## 2026-09-20 · 删除 · 「扔进回收站」根本没腾出空间（一个差点骗过自己的安全设计）

用户在上一轮搬迁后说「C 盘那边的删掉吧」，于是执行清理。

- **我做了什么**：把 `--purge` 从 `shutil.rmtree`（永久删）改成走 Windows 回收站
  （`SHFileOperationW` + `FOF_ALLOWUNDO`），觉得「更安全」。8 个源曲库、186 个文件全部清走。
- **问题**：回收站**就在同一块 C 盘上**。扔进回收站 = 把文件从 A 目录挪到 B 目录，
  **磁盘占用一点没少**。实测 C 盘已用从 **204.3 GB → 204.57 GB**（还涨了），
  回收站 7532.3 MB → 7831.4 MB（正好 +299.1 MB）。
  → 用户的目标是「腾出 C 盘」，我的「更安全」做法**完全没达成目标**，还多占了空间。
- **正确做法**：送回收站（可还原）→ 用户确认无误 → 再清掉回收站里那几条（永久删）。
  所以 `migrate_library.py` 补了 `--empty-bin`：
  解析回收站的 `$I` 索引文件拿到「原始路径」，**只清命中传入路径的条目**，不碰其它。
  （回收站 `$I` 格式：偏移 0 版本(=2) / 8 文件大小 / 16 删除时间 / 24 路径长度 / **28 起 UTF-16 原路径**）

### 顺带修掉的两个真 bug

1. **成功判据错了，误报「处理失败」**：
   `recycle()` 用 `SHFileOperationW` 返回值判断成败，实测**文件明明全进了回收站，
   它却返回非零**（因为它没能把空目录壳也一起收走）→ 8 个全部打印「✗ 处理失败」，
   差点让我以为没删成，也差点去编「权限问题」之类的解释。
   → 改成**行为判据**：删完再看「源目录下还剩不剩真文件」，0 个即成功。
   **又一条「别信 API 返回值，要看实际状态」**。
2. **残留空目录壳**：2 个目录（`mw-validation`、`music-factory`）下层留下 14 个
   **0 字节的空目录**。补 `prune_empty_dirs()` 用 `os.rmdir` 自底向上收掉 ——
   **只用 rmdir（只能删空目录）**，一旦目录里还有文件就抛错、保持原样，绝不强删。

### 验证方式（务必照做）

写 `empty_bin_for()` 时先做**隔离测试**：造一个 488 KB 的测试目录 →
`recycle()` → `empty_bin_for()` → 确认
① 命中条目真的被清掉、② **回收站总条目数 14352 → 14353 → 14352**（其它一条没误伤）。
**清回收站这种不可逆操作，必须先拿假数据跑通再上真数据。**

- **来源**：用户「C盘那边的删掉吧」

> **教训**：
> ① **「更安全」的做法要先确认它有没有达成用户的目标。** 回收站看着稳妥，
>   却让「腾出 C 盘」这个目标完全落空 —— 还得多占 299 MB。
>   **安全性和有效性不是二选一**：正确顺序是「先可还原地删 → 确认无误 → 再真正删掉」。
> ② **同一块盘上的回收站不是「删除」，是「搬家」。** 想真正释放空间，只有永久删。
> ③ **成功判据要用「可观测的结果」，不是「API 的返回值」。** 这次两者刚好相反。

## 2026-09-20 · 删除（续）· `--empty-bin` 因为「没东西可删」提前 return，永久清理永远不生效

用户确认「清掉，真正腾空间」后跑 `--purge-only --empty-bin`，结果**只打印了一句
「磁盘上的源目录已经清完了」就退出，回收站一条没清**。

- **根因**：`do_purge_only()` 里有个 `if not src_libs: return 0` 的**提前返回**。
  上一轮已经把源目录送进回收站，所以这次 `src_libs` 是空的 →
  直接走「没东西可删」分支 return，**后面的 `--empty-bin` 根本没机会执行**。
  于是出现最迷惑的状态：**命令成功退出、没有任何报错、空间却一点没腾**。
- **修复**：源已清空但带了 `--empty-bin` 时不再 return，改用
  **`all_src_libs`**（迁移报告里记录的**全部**源路径，含已删的）去清回收站。
  阶段三也从 `done` 改成 `all_src_libs` —— 只要还在回收站里就该一并清。

### ⚠️ 永久删除之前，必须做「孤儿交叉校验」（这一步真的救回了一个文件）

`--empty-bin` 不可逆。动手前把回收站每个条目按「原始路径去掉源前缀」得到相对路径，
逐条去目标盘对照，看有没有 **D 盘不存在的孤儿**：

```
265 / 266 条在 D 盘都有对应
  1 条孤儿：music-factory\library\霓虹深渊\cover_source.jpg
```

`霓虹深渊` 这首歌**在 D 盘完全没有** —— 它在**搬迁之前就更早被删掉**了，
只剩这张封面源图卡在回收站。差点被当成「顺手清掉的垃圾」永久销毁。

→ 处理：先 `copy2` 到 `D:\music-workflow\_recovered\霓虹深渊\`（8228 B 校验一致），
**再**执行清理。只有 8 KB，但**「零风险」比「省事」值钱**。

### 回收站条目数 ≠ 歌曲数（别被吓到，也别因此停手）

- 45 首歌 → 回收站里 **266 条**。因为 Windows 回收站是**按被删对象逐条记**的
  （每个文件一条 `$I`/`$R`，目录壳也各占一条），不是「一个 library 一条」。
- 所以「266 条远多于 45 首」是**正常**的；判断安全性靠的是**路径归属校验**，不是数量对得上。

### 最终结果（以磁盘实测为准）

| 指标 | 数值 |
|---|---|
| 清理前 C 盘已用 | 204.65 GB（可用 95.35 GB） |
| 清理后 C 盘已用 | **204.31 GB**（可用 95.69 GB） |
| 实际释放 | **348 MB** |
| 回收站剩余命中条目 | **0 条** |
| D 盘曲库 | 45 首 / 299.1 MB / 四件套零缺失 |

- ⚠️ **脚本自报「释放 305.2 MB」，实测磁盘少了 348 MB —— 两者不一致。**
  所以「腾出空间」这件事**只认磁盘数值**（`GetDiskFreeSpaceExW` 前后对比），
  脚本打印的 MB 数只能当参考。**别拿自报数字去回复用户。**

> **教训**：
> ① **「没东西可删」不等于「没事情可做」。** 提前 return 前先问一句：
>   用户真正想要的那个结果（腾空间）达成了吗？没达成就不该 return。
>   这次表现为「成功退出 + 无报错 + 目标落空」，是最难发现的一类失败。
> ② **不可逆操作前，用「交叉校验」找孤儿，而不是靠「应该都拷过了」。**
>   这次的孤儿恰好是**搬迁前就删掉的历史残留**，任何「比对迁移清单」的思路都发现不了它，
>   只有「逐条问目标盘有没有」才能捞出来。
> ③ **空间类操作以磁盘实测为准**，脚本自报数值可能与实际不符（本次差 43 MB）。

### 验证方式（可复用）

```python
# 清理前后各跑一次，用差值判断「是否真释放」
def disk(root):   # 返回 (free, total)
    f = ctypes.c_ulonglong(0); t = ctypes.c_ulonglong(0)
    ctypes.windll.kernel32.GetDiskFreeSpaceExW(ctypes.c_wchar_p(root),
        ctypes.byref(f), ctypes.byref(t), None)
    return f.value, t.value
```
清完再扫一遍回收站确认**剩余命中 0 条** —— 而不是只看脚本有没有报错。

- **来源**：用户「C盘那边的删掉吧」→「清掉，真正腾空间（推荐）」

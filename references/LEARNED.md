# 经验沉淀（每次解决卡点后必须往这里写）

> **这个文件是「卡点学习模式」的落地处。**
> 按 SKILL.md 的纪律 2：同一环节连续失败 2 次、或重试 3 次无进展，
> 就要请用户手动操作一遍并把过程回传，然后把学到的东西写进这里。
>
> 只改代码不写这里 = 下次还会踩同一个坑。

## 记录格式

```
## YYYY-MM-DD · 环节名 · 一句话现象

- **现象**：用户/脚本看到了什么
- **根因**：为什么会这样（不要只写"改了选择器"，要写为什么原来的不对）
- **解法**：具体改了什么（文件 + 关键代码/配置）
- **验证**：怎么确认真的解决了
- **来源**：自己debug / 用户手动操作后回传
```

## 2026-08-30 · MiniMax 生成 · Music 3.0 出歌时间约 10-13 分钟，默认 7 分钟超时不够

- **现象**：`generate.py` 提示「✓ 已点生成」后，轮询 `history_list` 7 分钟仍拿不到 `audio_url`，
  报「✗ 超时，没拿到音频链接」。查看 `history_list` 接口发现新条目已经产生，只是 `audio_url` 为空。
- **根因**：MiniMax Music 3.0 模型生成后需要后端转码，**实测耗时 10-13 分钟**才填上 `audio_url`。
  脚本默认 `wait_timeout_sec=420`（7 分钟）是在旧模型（生成+转码 1-3 分钟）时代测的，
  对 Music 3.0 不够用。超时后脚本重试，会再生成一组重复条目，浪费额度和时间。
- **解法**：把工作目录 `config.json` 的 `wait_timeout_sec` 从 `420` 提高到 `900`（15 分钟），
  并同步更新技能源文件 `scripts/config.json`。
  已经 pending 的条目不要重新生成，用 `_poll_pending.py` 这类轮询脚本等 `audio_url` 就绪后直接下载。
- **验证**：《老街的灯》在 13:20 点生成，13:32 才拿到音频（约 12 分钟）；
  把超时改成 900 秒后，《旧时月色》正常等到 `audio_url` 并下载完成。
- **来源**：自己 debug

> **教训**：页面提示「通常 1-3 分钟」只是参考；要以接口实际返回为准。
> 看到 `新作品已产生：等音频转码…` 说明生成已经成功，问题只是超时不够，不要急着重试。

## 2026-08-30 · MiniMax 生成 · 「找不到歌词输入框 / 找不到生成按钮」但元素明明存在

- **现象**：`generate.py` 在 MiniMax 页提示「✗ 找不到歌词输入框」「✗ 找不到生成按钮」，连续两次失败。
  但单独诊断脚本列出页面元素：歌词 `div[contenteditable='true']` 和生成按钮 `button:has-text('限时免费')` 都存在。
- **根因**：MiniMax 上线了「Music 3.0 创作者内测，限时免费畅玩」活动弹窗，结构是
  `<section class="fixed bottom-0 left-0 right-0 top-0 z-[1050] overflow-auto">`
  全屏覆盖，且内部还有一个 `<section class="responsive-modal ...">` 承载弹窗内容。
  这个弹窗**不在** `popup_guard.py` 默认的 `DEFAULT_POPUP_ROOTS` 白名单里（没有 `.ant-modal-*`，也没有 `[role='dialog']`），
  因此 `dismiss_popups()` 没找到关闭按钮 `button[aria-label='close']`，弹窗没被关，
  Playwright 点歌词框时报告 `<section ... z-[1050] ...> subtree intercepts pointer events`。
- **解法**：往 `config.json → popup_guard.extra_popup_roots` 增加两个选择器，让守卫能识别这个弹窗容器：
  ```json
  "extra_popup_roots": [
    "section.responsive-modal",
    "section[class*='z-[1050]']"
  ]
  ```
  同步更新技能源文件 `scripts/config.json`（`init_workdir.py` 会把它复制到新工作目录）。
- **验证**：运行 `_diag_lyrics.py` 复现 `generate.py` 的填表流程，日志显示
  `✓ 已关闭一个弹窗（关闭按钮）` → 歌词框 `wait_for OK / click OK / insert_text OK` → 生成按钮可见。
  随后正式跑 `generate.py` 也成功填词并点生成。
- **来源**：自己 debug

> **教训**：改版后的弹窗不一定是标准组件库（AntD/Arco），不能指望 `[role='dialog']`。
> 出现「元素存在但点不动」时，第一反应应该是**有全屏遮罩挡在前面**，查 `elementFromPoint` 比改选择器更快。

## 2026-08-30 · MiniMax 生成 · 点一次生成却出了两首歌（页面数量默认 2）

- **现象**：点一次生成，MiniMax 出了两首歌，额度白白浪费一半。
- **根因**：MiniMax 页面上的「生成数量」控件**默认值是 2**，脚本从来没设置过它。
  `config.json` 的 `quantity_per_round` 只是脚本"等几首结果"的预期值，
  **并不作用于页面** —— 两者碰巧都是 2 时看起来正常，一改成 1 就对不上了
  （页面出 2 首、脚本只取 1 首），属于典型的"配置看起来生效、其实没接上"。
- **解法**：
  1. `generate.py` 新增 `set_generate_quantity()`，在点击生成前把页面数量控件
     设成本轮需要的数字（`need`）。两条路径：能填就直接 `fill`，
     只读的 stepper 就点「减/加」按钮一步步走到目标值。
  2. `quantity_per_round` 默认从 2 改成 1（用户要求点一次出一首）。
  3. 数量控件选择器写进 `config.json → selectors.quantity`（input/minus/plus），
     页面改版时加选择器即可，不用改代码。
- **验证**：`test_popup_guard.py` 测试 16 覆盖三条路径
  （直接填值 2→1、只读控件点减号 3→1、已是目标值保持不动）。33/33 通过。
- **来源**：用户反馈

> **教训**：**配置项必须"接上"页面才叫生效。** `quantity_per_round` 写着 2，
> 页面默认也是 2，于是长期"看起来是对的"——直到改成 1 才暴露出它根本没连到页面上。
> 判断标准很简单：**改一下配置，看页面行为是否跟着变**，没变就是没接上。

## 2026-09-01 · MiniMax 生成 · 数量还是出两首（第一版修复没真修好）

- **现象**：上一版（08-30）改了 `quantity_per_round=1` 还新增了 `set_generate_quantity()`，
  用户实测**仍然一次出两首**。第一版只是"看起来修了"。
- **真实根因（比 08-30 想的更深）**：
  1. **控件形态猜错了**。MiniMax 音乐页是 **Next.js + Tailwind 自定义 UI，不是 antd**，
     数量控件是自定义 stepper：`<div>` 里放「数量:」标签 + 两个 `<button>`（减/加，只有 svg 图标、
     **无任何 class/aria 提示**）+ 一个纯数字 `<span>` 显示当前值。
     第一版写的选择器（`input[type=number]`、`[class*='minus']`、`ant-input-number`…）**一个都匹配不上**，
     于是函数走到"找不到控件"静默返回，页面数量纹丝不动。
  2. **定位逻辑也踩坑**。即便改成找「数量」标签，从标签往上找第一个含≥2按钮的祖先，
     会**误命中整块输入区的大容器**（里面有 14 个按钮，含「参考音乐上传」「生成」等），
     `btns[0]` 变成「参考音乐上传」按钮——点减号根本不作用于数量。
- **正确解法**：
  1. **定位**：找页面上的「纯数字 span」，它的**父容器恰好有 2 个按钮**的就是 stepper
     （第一个按钮=减、最后一个=加）。这样不会误命中大容器。
  2. **改值**：点减/加按钮一步步走到 `want`；点击用**原生 `el.click()`** 触发 React 合成事件，
     绕过 Playwright 的可点击性/遮罩检查（这类 Tailwind 自定义按钮常被误判为点不到）。
  3. `quantity_per_round` 默认 1 保留；`selectors.quantity` 的 input/minus/plus 仅作兜底（antd 等其它形态）。
- **验证（真页面，最有说服力）**：`verify_qty.py` 打开真实页面，
  读取修改前后值 —— 2→1、1→3、3→1 全部生效，函数返回 True。
  回归测试 `test_set_quantity.py` 用高度还原的合成 DOM（stepper 嵌在含 14 按钮的大容器里，
  专门复现"误命中大容器"）跑 4 项全过。
- **来源**：用户实测反馈「还是出两首」

> **教训（叠加 08-30）**：① 修"页面操作类"bug **不要猜 DOM 结构**——先用 `diag_qty.py` 抓真实 DOM 再写选择器；
> ② 定位祖先容器时，**优先用"最具体/最贴近目标"的锚点**（纯数字值 span → 父容器恰好 2 按钮），
> 别用"第一个满足条件的祖先"，那会命中范围过大的父节点；
> ③ 验证必须上**真页面**（或高度还原的合成页），合成页结构和真实差一个 class 都会让测试虚过。

## 2026-08-30 · 全环节 · 页面没铺满屏幕，底部按钮被挤出视口点不到

- **现象**：自动化打开的浏览器页面布局不完整，底部按钮（如「下一步」）被遮挡，很难点击。
- **根因**：`generate.py` 把浏览器视口**硬编码**成 `viewport={"width": 1440, "height": 900}`。
  在屏幕小于 1440×900 的设备上（实测 1280×720），页面按 1440 宽渲染，比屏幕还大，
  横向溢出 + 底部按钮落在视口外。`fanqie_upload.py` 虽然 `--start-maximized`，
  但没设 `viewport=None`，Playwright 默认视口 1280×720 照样覆盖窗口尺寸，页面不跟随窗口。
- **解法**：
  1. `browser_utils.py` 新增 `window_args(headless)` / `viewport_for(headless)`：
     有头模式 `--start-maximized` + `viewport=None`（页面跟随窗口自适应），
     headless 模式才给固定视口兜底。
  2. `generate.py`、`fanqie_upload.py` 全部改用它，删掉手写视口。
  3. 点击/填写前 `scroll_into_view_if_needed()`（长页面底部按钮先滚到可见）。
- **验证**：真起有头 chromium 实测，页面视口 = 屏幕可用尺寸（1280×720 = 1280×720）。
- **来源**：用户反馈（换设备后用） + 自己实测

> **教训**：**不要硬编码浏览器视口。** 固定 1440×900 只对作者自己的屏幕成立，
> 换台设备就溢出。正确姿势是"有头 = 最大化 + 跟随窗口，headless = 才给固定值"，
> 参数封装成公共函数让所有脚本共用（不然各写各的又会有漏网的）。
> 这台设备实测就是 1280×720 —— 固定 1440 的视口比屏幕还宽，必然溢出。

## 2026-08-30 · MiniMax 生成 · 守卫认不出弹窗容器（靠猜 class 名字的必然结局）

- **现象**：MiniMax 登录后弹活动公告（要手动点 ❌），守卫关不掉，生成流程卡死。
- **根因**：为了安全，关闭按钮的查找范围被限定在**已知弹窗容器白名单**里。
  但 MiniMax 的容器是 `<section class="responsive-modal z-[1050]">`，**不在名单里**，
  守卫连找都没往里找。用 `[class*='-close']` 也没用：❌ 的 class 是 `icon-btn`，不带 close。
- **解法**（三层，全部建立在"作用域"上，不是扫描整个页面）：
  1. **遮挡浮层作用域**（`use_overlay_scope`，默认开）：凡是
     `fixed/absolute + z-index≥100 + 覆盖≥40% 屏幕` 的元素，一律也算作用域。
     ★ **靠"它挡住了屏幕"这个行为识别，跟它叫什么名字无关** —— 这是根本性修复。
  2. **角落兜底**：× 连 close 类名都没有时，按「在对话框右上角 + 尺寸≤64px +
     内容是 ❌/×/✕」来认。
  3. 用户把实测到的容器选择器加进 `extra_popup_roots`（双保险）。
- **验证**：`test_popup_guard.py` 新增测试 12/13/14/15，覆盖
  「容器非标准」「❌ 无 close 类名」「MiniMax 真实结构（icon-btn）」
  「MiniMax 真实结构（aria-label='close'）」。30/30 通过。
- **来源**：用户反馈 + 用户补充真实容器选择器 + 自己写测试复现

> **教训（两个）**：
>
> 1. **靠名字识别不可靠，要靠行为。** 猜 class 名字（白名单）永远有漏网的，
>    因为网站可以起任何名字。而"它挡住了屏幕"是**行为层面**的判据，与命名无关。
>    安全与能力不是二选一 —— 把作用域限定到"确实构成遮挡的元素"，既安全又通用。
>
> 2. **角落兜底要按"对话框面板"的右上角算，不能按"整屏遮罩"的右上角算。**
>    这个 bug 我差点漏掉：对话框居中时（460px 宽 / 1440px 视口），它的右上角跟
>    遮罩的右上角差了近 500px，按遮罩算会**全部漏判**。
>    写完先跑测试才发现 —— 又是一次"不写真机测试根本发现不了"。

## 2026-08-30 · 全环节 · 打开页面后弹窗挡路，自动化卡住不动

- **现象**：打开 MiniMax 音乐创作页后有时弹出浮层，脚本不关掉就执行不了下一步，
  表现为「点了生成没反应」「填表填到一半卡住」。
- **根因**：两个层面都没处理。
  1. 脚本里全是裸 `page.goto()` 和裸 `click()`，**没有任何弹窗处理逻辑**
     （`grep dialog` 在两个脚本里都是 0 处命中）。
  2. 更隐蔽的是：最麻烦的浮层是「整屏半透明遮罩 + 没有关闭按钮」，
     它会把**关闭按钮自己也挡住**。所以哪怕写了"点 × 关闭"也照样点不动——
     Playwright 报 `intercepts pointer events` 然后超时。
- **解法**：新建 `scripts/popup_guard.py`（同步版给 generate.py，异步版给 fanqie_upload.py），
  按「点 × → 点文字按钮 → 按 Esc → **铲掉纯遮罩再回到第一步重来**」的顺序循环处理。
  判断"纯遮罩"的依据是内部**没有任何可交互元素**，真正的对话框因此被跳过、不会误删。
  集成点：`guard_context()` 挂原生弹窗处理器、`goto_with_guard()` 替换所有裸 goto、
  `try_click(..., cfg=cfg)` 点不动时自动清弹窗再重试一轮。
- **验证**：新增 `scripts/test_popup_guard.py`，真起 chromium 构造三种弹窗实测，**14/14 通过**。
- **来源**：用户测试反馈 + 自己 debug（先写测试跑出失败，才暴露出下面的两个实现 bug）

> **自己写的代码被自己的测试抓出两个 bug**（值得记下来）：
> 1. **顺序错了**——把"铲遮罩"当最后兜底，结果第一轮点 × 就被遮罩挡住，后面全废。
>    必须把铲遮罩纳入**每一轮**的升级链条。
> 2. **循环提前 `break`**——第 0 轮没命中就退出，根本走不到铲遮罩那一步。
>    正确做法是"一整轮下来什么都做不了"才 break。
>
> 这两个 bug 单看代码都很合理，**不写真机测试根本发现不了**。

> **顺带纠正一个想当然的说法**：我一开始在文档里写"原生 alert 不处理会让页面一直挂起"。
> 用对照实验验证后发现是错的——**Playwright 在没有 dialog 监听器时会自动关闭原生弹窗**，
> 通常不会卡住。真正危险的是 DOM 浮层。挂处理器的实际价值是：能看到弹窗说了什么
> （如"额度用尽"）、`beforeunload` 不会被自动关闭、以及排掉"别处注册了监听器却没处理"的雷。
> **没有验证过的断言不要写进文档。**

## 2026-08-30 · 分发环节 · 新增模块忘了加进 init_workdir 的复制清单

- **现象**：给 generate.py / fanqie_upload.py 加了 `import popup_guard`，
  在仓库目录里跑得好好的，但用户 `init_workdir.py` 新建的工作目录里**没有** popup_guard.py，
  一运行就 `ModuleNotFoundError`。
- **根因**：`init_workdir.py` 靠 `COPY_FILES` 列表决定复制哪些文件。
  新增一个**被 import 的模块**时，这个列表不会自动更新，也不会有任何报错——
  因为仓库目录本身文件是齐的，**只有在别人电脑 / 干净目录里才会炸**。
- **解法**：`COPY_FILES` 加上 `popup_guard.py` 和 `test_popup_guard.py`，
  并在列表上方写了醒目注释，说明"新增被 import 的模块必须同步加进这里"。
- **验证**：真跑 `python init_workdir.py <临时目录>`，再**切到那个目录**里跑
  `generate.py --help` / `fanqie_upload.py --help` / `test_popup_guard.py`，全部通过。
- **来源**：自己 debug（写完新模块后想到要验证分发链路，一试果然漏了）

> **教训**：**凡是"加了一个文件"的改动，都要问一句"它需要跟着分发吗"。**
> 验证方式是真的 `init` 一个干净目录再跑一遍，而不是在源目录里看它能不能启动——
> 源目录永远缺不了文件，这类 bug 在那里根本露不出来。

## 2026-08-30 · 番茄上传 · 弹窗守卫把用户已填的歌手名等四个标签全删了（最严重的一次）

- **现象**：上传多首歌时，从第 2 首开始，第 1 首卡片里已填好的
  「歌手名 / 词作者 / 曲作者 / 制作人」四个标签**全部被清空**。
- **根因**：为了让自动化不被弹窗卡住，我写了 `popup_guard.py` 自动关弹窗，
  实现方式是**在整个页面扫 class 里带 close 的图标**（`[class*='-close']`、
  `[class*='close-icon']`、`[aria-label='关闭']` 等 32 种）然后逐个点掉。
  但这四个字段是**标签式输入框**，每个已填好的标签旁边都有一个删除用的 ×
  （形如 `.tag-close-icon`）—— 它跟"关闭弹窗"的 × 长得一模一样。
  上传第 2 首歌时，页面上还留着第 1 首填好的四个标签，于是一次性全被点掉。
- **解法**（改的是设计，不是改选择器）：
  1. **关闭按钮只在「可识别的弹窗容器」里找**（`popup_roots` 白名单：
     `.ant-modal-root` / `.arco-modal-wrapper` / `[role='dialog']` / `[aria-modal='true']` 等 19 种），
     **绝不扫描整个页面**（`scan_whole_page` 默认 `false`）。
  2. `dangerous_selectors` 黑名单兜底：`.ant-tag-close-icon`、
     `.ant-select-selection-item-remove`、`[class*='clear-icon']` 等，命中即跳过。
  3. 文字拦截：含「删除 / 移除 / 清空 / 注销 / 解绑 / 放弃 / 终止」的按钮**一律不点**。
- **验证**：`test_popup_guard.py` 新增测试 6（已填标签一个不能少，同时真弹窗照关）、
  测试 10（"确认删除"弹窗宁可不管也不能点）。21/21 通过。
- **来源**：用户实测反馈 + 自己写测试复现（先写测试证明 4 个标签确实被删，再动手改）

> **教训（这条最该记住）**：**语义相反的两个控件可以有完全一样的外观和 class。**
> 「关掉弹窗」的 × 和「删掉这条内容」的 × 长得一模一样，靠猜 class 名字区分必然出事。
> 正确做法是**用"它在哪儿"来判断**（是否在弹窗容器内），而不是"它长什么样"。
>
> 更一般地说：**自动化去点页面上的东西之前，必须能回答"点了会发生什么"。**
> 答不上来就不要点 —— 宁可流程卡住让人来处理，也不能静默删掉用户的数据。
> 卡住是可见的、可恢复的；数据被静默清空则可能根本没人发现。

## 2026-08-30 · 番茄上传 · 弹窗要点「确认」而不是删掉遮罩（用户明确指出）

- **现象**：我原先用"删掉挡路的整屏遮罩"作为兜底手段，保证点击能进行下去。
- **用户反馈**：「弹窗信息你只要点确认就好了，它会自动关闭，不用总是删掉，
  这样会误删一些重要的弹窗信息，影响后面执行」。
- **根因**：删遮罩是**绕过页面自身逻辑**的粗暴做法 —— 直接把 DOM 移除，页面却以为
  弹窗还开着，内部状态不一致；更要命的是会连带干掉那些**需要人看一眼**的重要弹窗
  （额度提醒、验证提示、授权确认），后面的步骤反而因此出错。
- **解法**：策略改成"先礼后兵"——
  ① × 关闭按钮 → ② 弹窗底部主按钮（番茄裁剪弹窗就是这种，文案可能是"确定/保存/完成"）
  → ③ 确认类文字按钮 → ④ 关闭类文字按钮 → ⑤ Esc → ⑥ 删遮罩（**默认关闭**）。
  点确认走的是页面自己的关闭流程，弹窗会自己关掉，页面状态也保持一致。
- **验证**：测试 7（"我知道了"必须压过"以后再说"）、测试 8（遮罩默认保留，
  显式 `force_mask=True` 才删）、测试 9（Arco footer 主按钮能认出来）。
- **来源**：用户反馈

> **教训**：**优先走页面自己的正常路径，不要绕过它。**
> 点"确认"是页面设计好的关闭方式，删 DOM 是硬来。能用正常路径就别用 hack。
> 这也解释了上一版的删遮罩为什么错：它解决了"点不动"这个表象，
> 代价是破坏页面状态 —— 典型的"治标，且带来新问题"。

## 2026-08-30 · 歌名含逗号 · safe_name 会把全角标点转成半角（验证中发现的隐患）

- **现象**：歌名《晚风，寄的信》经 `generate.py` 的 `safe_name()` 处理后，
  文件夹名变成 `晚风,寄的信`——中文全角逗号「，」被转成了英文半角逗号「,」。
- **根因**：`safe_name()` 里用了 `unicodedata.normalize("NFKC", name)`。
  NFKC 归一化会把全角标点统一转成半角，而**英文逗号不在非法字符过滤列表里**
  （列表只过滤 `\/:*?"<>|`），于是半角逗号被保留下来。
- **为什么危险**：`fanqie_upload.py` 的 `--mark-published` 和 `--songs`
  都是**用英文逗号分隔**参数的。一旦歌名含半角逗号，
  `--mark-published 晚风,寄的信` 会被拆成「晚风」和「寄的信」两个名字，
  防重复记录会静默失效（不报错，但记为错误的名字，下次照样重复发）。
  同理，上传到番茄平台的歌名会显示成半角逗号，中文排版下很难看。
- **根本修复（已完成）**：`safe_name()` 里加一行 `name.replace(",", "，")`，
  归一化后把半角逗号换回全角——既保住中文排版，又不会被参数分隔符误伤。
- **用法提醒**：尽管如此，歌名仍建议尽量简洁、少用标点。
- **验证**：改用无逗号歌名后，`safe_name()` 输出与原歌名一致，`--mark-published` 解析正常。
- **来源**：自己 debug（本次「发布前再验证一遍」时扫描出来的）
- **教训**：**NFKC 归一化 + 逗号分隔参数 = 静默失效的定时炸弹**。
  凡是"用户输入会变成文件名、又会被塞进逗号分隔列表"的地方都要查一遍。

> ⚠️ **写文档时的注意事项**（2026-08-30 公开前扫描发现）：
> 本文件在记录这个坑时，曾直接用**真实作品名**当例子，
> 结果把使用者的实际作品信息带进了公开仓库（写这条教训时又差点犯同样的错）。
> **规则：文档、模板、注释里举例一律用虚构歌名**（如《晚风，寄的信》），
> 绝不出现任何真实发布过的作品名。每次公开前按同样方式扫一遍。

> 顺带：这次是用户要求「上传前再验证一遍 skill 是否可靠」才发现的。
> **没跑过的路径就是没验证过的路径**——之前的歌名恰好都没逗号，所以从没暴露。

- **根因**（a3cc6d6 的盲区）：之前那版只解决了**番茄上传页**跟随窗口（`--start-maximized` +
  `viewport=None`），但**第三方的电子签合同页**有三个 a3cc6d6 完全没考虑的问题：
  1. **合同页是「跳转授权」后新开的标签**，脚本没把它 `bring_to_front()`，用户看着的是番茄页
     以为"页面没反应"——其实合同页在背后开着。
  2. **合同页常被 fixed 浮层盖住**：下载APP 横条、cookie 同意条、扫码关注等都是
     `position:fixed; bottom:0; right:0`，正好压在右下角的「确认签署」按钮上方。
  3. **a3cc6d6 的 `scroll_into_view_if_needed()` 只滚了"跳转授权/确认签署"等脚本自己点的按钮**，
     真正需要用户手动点的「确认签署」（第三方电子签平台，文案常是「签署 / 签字 / 提交」）
     没人帮它滚出可视区。
- **解法**（`fanqie_upload.py` 新增 3 个函数 + 2 处接入点）：
  1. **`fit_window_to_screen(page)`** — 启动后取 `window.screen.availWidth/availHeight`
     显式 `set_viewport_size`，把窗口 resize 到铺满屏幕。即使 `--start-maximized` + `viewport=None`
     也兜底一层（150% DPI 下偶尔窗口没填满）。
  2. **`dismiss_cover_overlays(page)`** — 遍历 DOM，命中 `position: fixed/absolute` 且
     文本含「下载/APP/小程序/扫码/cookie/引导/广告」等关键词的浮层 → `display:none`。
     严格不动正文内容。
  3. **`ensure_sign_clickable(cpage, log)`**（★ 核心）：
     - `cpage.bring_to_front()` — 合同标签送最前；
     - 调 `dismiss_cover_overlays`；
     - 强制 `html/body { overflow:auto }` 确保可滚；
     - 找 `签署/确认签署/签字/提交…` 类按钮，`scrollIntoView({block:'center'})` 滚到正中；
     - **精确移除「盖在按钮中心」的元素**（`elementFromPoint(btn中心)` → 向上找最近的
       `fixed/absolute` 父级 → `display:none`），返回处理结果（`ok / dismissed / covered-by-static`）；
     - 截图 `_fanqie_contract.png` 供肉眼核对右下角按钮是否在可视区、能否点到。
  4. 接入点：① `--login` 和主流程两处 `launch_persistent_context` 之后调
     `await fit_window_to_screen(page)`；② `step3_sign_contract` 拿到 `cpage` 之后
     `await ensure_sign_clickable(cpage, log)`。
- **验证**（真页面 + 模拟页面双保险）：
  - **模拟页**（`scripts/verify_sign_view.py`）：写一段本地 HTML 复现"右下角签署按钮被
    fixed「下载App」浮层盖住"，复用 `fanqie_upload.ensure_sign_clickable` 跑同样的修复逻辑。
    运行结果：
    ```
    修复前 按钮中心命中元素 : cover     （被遮挡）
    修复后 按钮中心命中元素 : signbtn   （可点）
    按钮实际可点击        : True
    ✅ 验证通过：遮挡已清除，右下角签署按钮可点击。
    ```
    截图 `_verify_before.png` / `_verify_after.png` 肉眼可看出黑色「下载App」条消失、
    红色「确认签署」按钮出现在右下角。
  - **真页面**（下次你跑第三步时）：脚本到这一步会**自动**跑这套修复 + 截图
    `_fanqie_contract.png`，如果按钮被挡，处理结果会打在日志里
    （`✓ 定位到签署按钮「签署」（遮挡处理：dismissed:DIV）`）。
- **来源**：用户实测反馈（第三步最后签合同时按钮点不到）+ 自己写 `verify_sign_view.py`
  复现 + 跑通后再部署到线上

> **教训（叠加 a3cc6d6）**：
> ① 修"页面不跟随窗口"类 bug，**只修主流程页面不够**，要追到**所有用户要手动操作的页面**
> （含第三方新开标签）才算修完。a3cc6d6 解决"上传页"，但忽略了"合同页"。
> ② 浮层遮按钮是**行为层问题**，用 `elementFromPoint(按钮中心)` 看实际命中谁最可靠，
> 比"加 z-index 兜底"或"调 selector 顺序"都准。
> ③ **截图是验证的硬证据**。给人看 before/after 截图（不只是日志）才能让"遮挡"这种
> 视觉问题有可复核的产物。`verify_sign_view.py` 就是把"我修了"变成"你能看到我修了"。

## 2026-09-01 · 登录态隐私红线（skill 多人共用，绝不能泄露个人账号）

**现象**：用户明确提醒——这个 skill 是给很多人用的，每人各自登录自己的账号，
**不能泄露任何人的登录信息**。

**根因（之前埋的雷）**：代码把浏览器登录态写成 `PROFILE = ROOT / "profile_fanqie"`，
也就是登录态目录 `scripts/profile_fanqie/`（77M 真实 Cookie/LocalStorage）和 `scripts/profile/`
（MiniMax，33M）**躺在 skill 文件夹内**。skill 文件夹一旦被拷贝/分发，登录态就跟着泄露。
（git 侧没问题：`.gitignore` 早就忽略了 `profile*/`，从未提交过历史；但**磁盘上的目录**
才是真正会被"拷文件夹"带走的隐患。）

**解法（统一收口到 `scripts/paths.py` 的 `user_profile(name)`）**：
- `user_profile(name)` 返回 `%LOCALAPPDATA%/music-workflow/profiles/<name>`
  （Windows）/ `$XDG_CACHE_HOME/music-workflow/profiles/<name>`（Linux/macOS），
  **每用户私有、不在 skill 内**。
- 全量替换：fanqie_upload(generate/diag_qty/verify_qty/inspect_buttons/login_check/
  probe_generate/probe_popup 里所有 `ROOT / "profile*"` → `user_profile(...)`。
- 把磁盘上真实的两个 profile 目录 `shutil.move` 到新位置（**保留用户登录，不要求重登**），
  并删除验证遗留的合成 `_verify_profile`。
- `init_workdir.py` 不再建 workdir 里的 `profile/`、`profile_fanqie/`；`verify_sign_view.py`
  的临时 profile/截图改写到 `tempfile.mkdtemp()`，绝不落 skill 目录。
- `.gitignore` 保留 `profile*/` 等规则作双重保险。

**验证**：`python -c "import paths; print(paths.user_profile('profile_fanqie'))"` →
`C:\Users\<你>\AppData\Local\music-workflow\profiles\profile_fanqie`；
`scripts/` 内已无 `profile*` 目录；全部改动脚本 `py_compile` 通过。

> **教训（隐私/分发）**：
> ① 凡是"多人共用、会被拷贝分发"的 skill，**用户数据（登录态/作品/手机号）必须存在
> skill 文件夹之外**。约定俗成写 `ROOT / "xxx"` 是反模式——它把数据直接塞进可分发目录。
> ② 检查泄露不能只看 git 历史（`git ls-files` 空≠安全），更要看**磁盘上 skill 目录里
> 有没有真实数据文件**。用户是"拷文件夹"用，不是"clone 干净仓库"用。
> ③ 登录态这类敏感数据，迁移时优先"移动到每用户私有目录"而非"删了让用户重登"，
> 既消除泄露面又保住体验。
> ④ 加一道"改完 grep `ROOT / \"profile` 确认无遗漏"的纪律，防后人回归。

## 2026-09-01 · 数量控件改了"别的数字" · set_generate_quantity 静默误命中（第三版修复）

- **现象**：用户截图铁证——页面「数量：2 +」**仍然是 2**，
  但脚本日志写 `✓ 生成数量已设为 1（原 2）`。结果每首歌词点一次生成出 **2 个版本**
  （《陪你慢慢变老》×2、《母亲的缝纫机》×2），用户明确要求"一首词出一首"。
- **根因（比前两版更深）**：
  `set_generate_quantity()` 的 JS_FIND 用「纯数字 span + 父容器恰好 2 个按钮」定位 stepper。
  但页面上**不只有一个满足此条件的数字 span**——可能还有其他控件（标签数字、计数器等）
  也恰好是"数字 span + 父容器有 2 按钮"。脚本**命中了错误的那个**，点了它的减号，
  读回值确实从 2 变成 1（因为改的就是那个错误控件的值），于是报"已设为 1"——
  **真正的数量控件纹丝未动**。
  这是"看起来成功了"的**最阴险形态**：不是报错、不是超时，而是**静默改错了对象还报成功**。
- **正确解法（锚定「数量」标签）**：
  JS_FIND 必须先找含 **「数量」** 文字的标签元素（兼容 `数量：` / `数量:` / `数量`），
  再从这个标签的父/兄弟容器里定位数字 span + 减/加按钮。
  这样即使页面上有其他"数字+2按钮"的控件也不会被误命中——
  因为只有**紧挨着「数量」标签的那个**才是真正的 stepper。
  兜底保留旧逻辑（页面改掉标签文字时降级）。
- **附带修：生成按钮文案又变了**
  按钮探测显示按钮文本现在是 `600\n创作`（额度+换行+"创作"），
  不再是之前任何一期候选（`限时免费`/`一键音乐`/…）。
  在 `config.json → generate_button` 列表最前面插入 `button:has-text('创作')`。
- **验证**：修复后重跑 `generate.py`，日志应显示数量真正从 2→1 且生成按钮匹配到「创作」。
- **来源**：用户截图反馈「这里显示两首」→ inspect_buttons.py 探测真实按钮 → 定位根因并修复

> **教训（叠加前三轮）**：
> ① **"纯结构定位"（数字 span + N 个按钮）在复杂页面上必然碰撞**——
>   页面有多少个"数字+2按钮"的控件，你的选择器就能命中多少个。
>   **必须用语义锚点（「数量」标签文字）缩小范围**，而不是靠 DOM 结构猜。
> ② **"日志报成功 ≠ 真的成功"**——尤其涉及"改页面状态"的操作，
>   必须用**独立方式验证**（读回页面实际显示值 / 截图核对），不能只信自己的读写闭环。
> ③ **用户截图是最硬的证据**——脚本说"已设为 1"，用户截图显示"仍是 2"，
>   这类矛盾出现时**永远信用户的眼睛**，脚本的判断可能是基于错误元素的。

# 经验沉淀（每次解决卡点后必须往这里写）

> **这个文件是「卡点学习模式」的落地处。**
> 按 SKILL.md 的纪律 2：同一环节连续失败 2 次、或重试 3 次无进展，
> 就要请用户手动操作一遍并把过程回传，然后把学到的东西写进这里。
>
> 只改代码不写这里 = 下次还会踩同一个坑。

## 记录格式

```
### YYYY-MM-DD · 环节名 · 一句话现象

- **现象**：用户/脚本看到了什么
- **根因**：为什么会这样（不要只写"改了选择器"，要写为什么原来的不对）
- **解法**：具体改了什么（文件 + 关键代码/配置）
- **验证**：怎么确认真的解决了
- **来源**：自己debug / 用户手动操作后回传
```

## 2026-08-30 · MiniMax 生成环节 · 点了生成却永远等不到歌

- **现象**：脚本点完生成，等 7 分钟都拿不到音频链接，最后超时。
- **根因**（两个 bug 叠加）：
  1. `config.json` 的 `generate_button` 写成「一键音乐/生成音乐」，
     而 MiniMax 真实按钮文字是**「限时免费」**（底部紫色大按钮，⟳ 图标容易被误读成别的字）。
     从硬编码 selector 搬到 config.json 时搬错了。
  2. 出歌后**页面不会自动刷新历史列表**，脚本只会干等嗅探器抓包，所以永远等不到。
- **解法**：
  1. `config.json` 的 `generate_button` 改回 `button:has-text('限时免费')` 打头 + 多个兜底。
  2. `generate.py` 新增 `fetch_history()`，主动轮询
     `https://www.minimaxi.com/v1/api/music/history_list?...`，按 `music_id` 比对发现新作品。
- **验证**：日志出现 `✓ 新作品已产生：xxx（music_id=...）`。
- **来源**：自己 debug（用 `probe_generate.py` 抓后台接口 + `inspect_buttons.py` 列按钮属性）

> **衍生坑**：新作品刚出现时 `audio_url` **是空的**（音频还在转码），
> 必须继续轮询等到 `audio_url` 就绪再下载，否则会误判"超时没拿到链接"。

## 2026-08-30 · 番茄封面上传 · 卡在裁剪弹窗

- **现象**：封面上传后弹出裁剪框，脚本没点"确定"，弹窗挡住后续所有操作。
- **根因**：脚本找 `.cropper-modal`，但番茄实际弹窗是 **`.arco-modal-wrapper`**（arco 组件库）。
- **解法**：裁剪确认选择器改为
  `.arco-modal-wrapper button.arco-btn-primary`（并保留 `.cropper-modal` 兜底）。
- **验证**：日志出现 `✓ 已点裁剪确认` + `✓ 裁剪弹窗已关闭 → ✓ 封面已上传`。
- **来源**：自己 debug

## 2026-08-30 · 番茄第三步 · 死等「发布」按钮（最严重的一个）

- **现象**：脚本在第三步空转刷异常，日志不停报 `发布按钮可见性检查异常`，用户等了一整晚。
- **根因**：**番茄音频上传页根本没有「发布」按钮。**
  正确终点是：确认签署 → 等合同生成 → 点「跳转授权」→ 用户本人收短信验证码**签电子合同**。
  **签完合同 = 发布成功。** 脚本在等一个不存在的东西。
- **解法**：`step3_publish` 整个重写为 `step3_sign_contract(page, ctx, folders)`：
  - 第三步统一负责 `click_jump_authorize`（第二步不再重复点）
  - `find_contract_page()` 处理跳转后可能新开标签页的第三方电子签平台
  - 轮询所有标签页文本，匹配「签署成功/签署完成/签约成功/合同已生效」等 9 个关键词
  - 检测到签署成功**自动写 `published.json`**
  - `SIGN_WAIT_SEC = 1800`（30 分钟），每 60 秒打一次等待心跳
- **验证**：两首歌完整走完流程并发布成功。
- **来源**：**用户手动操作后告知**（这类"页面根本没有这个按钮"的事实，
  脚本自己 debug 一万年也发现不了——这正是纪律 2 存在的意义）

## 2026-08-30 · 登录环节 · 点了登录没反应 / 弹窗一闪就消失

- **现象**：点登录按钮后弹窗一闪就没了，或者点了完全没反应。
- **根因**：平台风控识别出自动化浏览器（Playwright 的自动化特征）。
  另外若用户自己开着另一个占用同 profile 的 Chrome，会把 profile 锁死导致页面无响应。
- **解法**：用 `login_check.py <平台>`（带反自动化检测 + 弹窗捕获 + 自动截图 + 自动判定）。
  运行前先确认没别的 Chrome 占着同 profile。
- **验证**：能正常弹出并保持登录窗，登录成功后脚本自动判定并保存登录态。
- **来源**：自己 debug

## 2026-08-30 · 代码层 · 两个 Python 低级错误

- **现象**：第三个环节报 `'async_generator' object is not iterable`；
  另有 `can only concatenate str` 类型错误。
- **根因**：
  1. 在**生成器表达式里用了 `await`**（Python 语法不允许）：
     `sum(1 for i in range(await x.count()) if await x.nth(i).is_visible())`
  2. `log("..." + LOG_PATH)` —— `LOG_PATH` 是 `Path` 对象没转 `str`。
- **解法**：改回普通 `for` 循环逐个判断；拼接处加 `str()`。
- **验证**：两个脚本 `py_compile` 通过。
- **来源**：自己 debug
- **教训**：**改完代码必须 `py_compile` 一次**，语法错误会让脚本在最关键的第 3 步才炸。

## 2026-08-30 · 分发前 · Mac/Linux 用户会静默失效

- **现象**：`taskkill /f /im chrome.exe` 是 Windows 专用命令，Mac/Linux 上会失败。
- **根因**：清理残留浏览器时直接写了 Windows 命令，且被 `try/except` 吞掉，
  **静默失效**比报错更危险（profile 被锁，用户完全不知道为什么打不开）。
- **解法**：新建 `scripts/browser_utils.py`，`kill_browsers()` 按
  `platform.system()` 分派（Windows=taskkill，Darwin/Linux=pkill），
  三处调用点改为调用它（保留原命令兜底）。
- **验证**：6 个脚本 `py_compile` 通过；跨平台代码路径已就位（**Mac 真机未实测**）。
- **来源**：自己做的开源前审计

## 2026-08-30 · 歌名含逗号 · safe_name 会把全角标点转成半角（验证中发现的隐患）

- **现象**：歌名《晚风，寄的信》经 `generate.py` 的 `safe_name()` 处理后，
  文件夹名变成 `妈,我回来了`——中文全角逗号「，」被转成了英文半角逗号「,」。
- **根因**：`safe_name()` 里用了 `unicodedata.normalize("NFKC", name)`。
  NFKC 归一化会把全角标点统一转成半角，而**英文逗号不在非法字符过滤列表里**
  （列表只过滤 `\/:*?"<>|`），于是半角逗号被保留下来。
- **为什么危险**：`fanqie_upload.py` 的 `--mark-published` 和 `--songs`
  都是**用英文逗号分隔**参数的。一旦歌名含半角逗号，
  `--mark-published 晚风,寄的信` 会被拆成「晚风」和「寄的信」两个名字，
  防重复记录会静默失效（不报错，但记为错误的名字，下次照样重复发）。
  同理，上传到番茄平台的歌名会显示成半角逗号，中文排版下很难看。
- **根本修复（已完成）**：`safe_name()` 里加一行 `name.replace(",", "，")`，
  归一化后把半角逗号换回全角——既保住中文排版，又不会被参数分隔符误伤。
- **用法提醒**：尽管如此，歌名仍建议尽量简洁、少用标点。
- **验证**：改用无逗号歌名后，`safe_name()` 输出与原歌名一致，`--mark-published` 解析正常。
- **来源**：自己 debug（本次「发布前再验证一遍」时扫描出来的）
- **教训**：**NFKC 归一化 + 逗号分隔参数 = 静默失效的定时炸弹**。
  凡是"用户输入会变成文件名、又会被塞进逗号分隔列表"的地方都要查一遍。

> ⚠️ **写文档时的注意事项**（2026-08-30 公开前扫描发现）：
> 本文件在记录这个坑时，曾直接用**真实作品名**当例子，
> 结果把使用者的实际作品信息带进了公开仓库（写这条教训时又差点犯同样的错）。
> **规则：文档、模板、注释里举例一律用虚构歌名**（如《晚风，寄的信》），
> 绝不出现任何真实发布过的作品名。每次公开前按同样方式扫一遍。

> 顺带：这次是用户要求「上传前再验证一遍 skill 是否可靠」才发现的。
> **没跑过的路径就是没验证过的路径**——之前的歌名恰好都没逗号，所以从没暴露。
